# Threat model: generated Viewer Apps

Scope: a Viewer App generated by the CerebroNexus Builder (`duocang/CerebroNexus`, branch `builder/03_builder`, commit `001c4d4dd68a6fc5c2c958d7c0c2a49961671b95`, version 6.0.0; not a release; controls changed by the fixes `c5462c264`, `58a604a0d` and `33150d9d7` are marked) and started with `shiny::runApp()` from its App directory. Written from the code of that commit; the tests that check it are experiment E (`scripts/E_security.R`, `results/E_security.csv`, README section E).

## How a generated App is put together

| Part | Where | Served over HTTP |
|---|---|---|
| `app.R`, `cerebro_config.rds` (options, dataset catalog, `.viewer_auth` descriptor) | App root | no (Shiny serves only registered resource paths, not the App directory) |
| Viewer code | `viewer/*.R` | no |
| Viewer static assets (JS, CSS, logo) | `viewer/www/` | yes, under the process-wide prefix `cerebro_www[_N]` (`shiny_UI.R`, `addResourcePath()`), before and after login; package code only, no data |
| CRB files, HDF5 sidecars (`<stem>.h5`), immune sidecars (`<stem>.immune.qs2`), external spatial images, Viewer Packs | `private-data/` (the bundle contract rejects CRB and sidecar paths outside it, `app_bundle/build.R`) | not as files. They are read by the R process; data reach the browser only through the session: websocket messages, session data objects (`/session/<token>/dataobj/...`: gene choices, spatial images through `viewerPrivateImageUrl()`) and, for datasets with a Viewer Pack, per-session static prefixes `cerebro-<kind>-<session token>-<n>` (`viewerStaticResourcePrefix()`, removed in `session$onSessionEnded`) |
| Login (optional) | `private-data/auth/credentials.sqlite` (shinymanager database, tables encrypted with a 64-hex-digit key), `viewer-auth.env` (that key, mode 0600) in the App root | no |

With login enabled, `viewer_auth_apply()` (`viewer/auth.R`) wraps the Viewer UI in `shinymanager::secure_app()` and starts the Viewer server function only after shinymanager has set an authenticated user. The Builder creates the accounts (at most 50, passwords of at least 8 characters, `app_bundle/auth.R`), generates a random key, writes the database encrypted with it, and writes the key to `viewer-auth.env` in the App; the timeout is fixed at 15 minutes. A key supplied as the environment variable `CEREBRO_AUTH_PASSPHRASE` takes precedence over the file.

## Assets

1. Dataset content: expression values, cell barcodes, metadata and group labels, projections, spatial coordinates and images, immune repertoire, HLA data.
2. Credentials: account passwords, the database key, shinymanager login tokens, Shiny session tokens (they name the session data URLs).
3. The integrity of what a user sees (the right dataset, the user's own selections).

## Actors

| Actor | Capability assumed |
|---|---|
| A. Unauthenticated network user | reaches the App's HTTP port; can send any HTTP request and websocket message; has no account |
| B. Authenticated user of another App or dataset | holds a valid account or token for a different generated App, possibly on the same host |
| C. Authenticated user of this App | holds an account of this App and runs a concurrent session next to another user's |
| D. Local OS user | an account on the server host other than the one running the App |
| E. Operator / author | builds and deploys the App; trusted |

## Trust boundaries

1. Network to the R process (HTTP and websocket). Everything a browser sends is untrusted.
2. Login: shinymanager's authentication state, held in the R process, decides whether the Viewer server function runs for a session.
3. Between sessions of one R process: inputs, outputs and reactive state are per session; `addResourcePath()` prefixes and `registerDataObj()` URLs are reachable by any client that knows the URL (they are capability URLs named by the session token).
4. File system: App directory and `private-data/` versus other OS users; the file mode of `viewer-auth.env` (0600, enforced at startup), the database (0600) and `private-data/auth` (0700).
5. Builder output to deployment: the App directory is copied to the server by the operator.

## Threats and controls

| # | Threat | Actor | Control in the code | Tested |
|---|---|---|---|---|
| T1 | Fetch data files by URL or path traversal | A | no static route to the App root or `private-data/`; static prefixes only for `viewer/www` and per-session Viewer Pack directories | E02, E25 |
| T2 | Data in the login page or websocket before login | A | Viewer UI rendered by `secure_app()` only for a valid token; Viewer server started only after login | E01, E03 |
| T3 | Guess session data URLs | A | URLs contain the 32-hex-digit Shiny session token; registered only after login | E03, E10 |
| T4 | Password guessing | A | shinymanager compares against hashed passwords. On 001c4d4dd no lockout or throttling (the Viewer loads the credentials table into memory, so shinymanager's `pwd_mngt` counters are not used); from `58a604a0d` failures are counted per account and per client address, with a wait from the fifth failure (30 s doubling to 15 min) during which the password is not checked | E04-E08 |
| T5 | Replay of the shinymanager token from the post-login URL (`?token=...`; `keep_token = FALSE` clears it from the address bar) | A, C | token valid while its session lives; removed on logout and timeout. | T8 | Account or token of one App used on another | B | each App has its own database and token store | E15 |
| T9 | Credentials read from disk | D | database tables encrypted, passwords hashed; key file 0600 and checked at startup (not a symlink, mode 0600, exact format) | E16, E17, E20-E24 |

| T12 | Expression data replaced on disk with a valid file of the same shape | D (write access to the App) | from `33150d9d7` the H5 sidecar's MD5 recorded at export is checked when it is read; the immune sidecar had a checksum already | F3 |

## In scope

- The generated App as started by `shiny::runApp()` on its App directory, with and without login, on one host.
- HTTP and websocket access from the network to that process, the login lifecycle (wrong, empty and repeated passwords, logout, timeout, token replay), isolation of concurrent sessions, cross-App accounts and tokens.
- Credentials at rest in the App directory, the database key, and secrets in Builder outputs and logs.
- Startup checks on the authentication files.

## Out of scope

- Serialized R inputs are trusted. Source objects given to the Builder and CRB/RDS/qs2 files are deserialized with R's readers and are assumed to come from the author. An App built with "show upload UI" turns every user of that App into a supplier of serialized R objects (`viewer/load_data/select_file.R`, `fileInput` for `.crb`/`.rds`); such Apps should be offered only to trusted users. The Builder's default is off and the E Apps were built with it off.
- TLS, reverse proxies, access logs, HTTP security headers, network exposure, host hardening and service accounts are deployment responsibilities, as the manuscript states. In particular the login token appears once in a request URL, so proxy access logs that record query strings would record it, and login over plain HTTP sends passwords in clear text.
- Per-dataset authorization: login is per App. Every account of an App can open every dataset of that App.
- Account management after export (adding users, password changes, admin mode: `enable_admin = FALSE`).
- Denial of service and resource exhaustion; browser-side attacks on the user's machine; supply-chain integrity of R packages.
- Confidentiality against the OS account that runs the App or root: that account must read the key to start the App, so it can decrypt the database.

## Deployment recommendations

- The Builder writes the database key to `viewer-auth.env` (mode 0600) in the App root, next to the encrypted database, so anyone who can read the App directory can decrypt the credentials. On a shared host, supply the key to the service as `CEREBRO_AUTH_PASSPHRASE` (it takes precedence over the file) and remove `viewer-auth.env` from the deployed copy; keep the original with the database.
- Serve the App over HTTPS, and do not log query strings at the proxy (the login token passes once in a URL).
- Behind a reverse proxy the per-client sign-in limit counts the proxy's address, so it then applies to all users together; the per-account limit is unaffected.
